# CloudGallery

A Google-Photos-style photo app for the PC. Upload photos, organise them in albums, favourite / bin / restore,
select thousands at once, share links, and watch your cloud storage and analytics.

**Stack:** React 19 + Vite + Zustand + TanStack Query + Recharts · FastAPI + MongoDB Atlas · Local / Cloudinary / S3-R2 storage · Electron desktop shell.

```
PhotoGalleryApp/
├── backend/    FastAPI (Swagger at /docs)
└── frontend/   React app + electron/ (desktop wrapper)
```

---

## 1. Run it (3 steps)

### Backend
```bash
cd backend
python -m venv venv
venv\Scripts\activate          # Windows   (Mac/Linux: source venv/bin/activate)
pip install -r requirements.txt
copy .env.example .env         # then fill MONGODB_URI (an existing .env is already included)
uvicorn app.main:app --reload
```
Open **http://localhost:8000/docs** - this is Swagger. Click **Authorize** after logging in to try every endpoint.

### Frontend (browser)
```bash
cd frontend
npm install
npm run dev                    # http://localhost:5173
```
Create an account on the login screen and start uploading (or drag photos onto the window).

### Desktop app (Electron)
```bash
cd frontend
npm run electron:dev           # starts Vite + Electron, and the backend automatically (CG_START_BACKEND=1)
npm run electron:build         # creates a Windows installer in frontend/release/
```
Electron extras: native file picker, system-tray (closing the window hides it), drag-and-drop from Explorer,
and **Settings → Sync folder** (auto-uploads new images that appear in a folder).

> Installer note: the installed app starts the bundled backend with `python` from your PATH. Install the backend
> requirements for that Python, and put your settings in `%APPDATA%/CloudGallery/backend.env` (same keys as `.env.example`).

## 3. Environment variables (`backend/.env`)

| Key | Meaning |
|---|---|
| `MONGODB_URI`, `DATABASE_NAME` | MongoDB Atlas connection |
| `JWT_SECRET` | Long random string that signs login tokens |
| `STORAGE_PROVIDER` | `local` (default), `cloudinary` or `s3` |
| `MAX_UPLOAD_MB`, `QUOTA_GB` | Per-file limit, per-user quota |
| `CORS_ORIGINS` | Allowed frontends (`null` = Electron built app) |
| `CLOUDINARY_*` | Cloud name / key / secret |
| `S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | AWS S3 or Cloudflare R2 |
| `S3_ENDPOINT_URL` | R2 only: `https://<account>.r2.cloudflarestorage.com` |
| `S3_PUBLIC_BASE_URL` | Optional CloudFront / R2 public domain (empty = presigned URLs) |

Frontend: `VITE_API_URL` (default `http://localhost:8000`).

## 4. Cloud services - learn them one by one

All storage goes through one interface (`backend/app/services/storage/base.py`). Routers never import boto3 or cloudinary,
so changing provider = changing config. Every photo remembers *which* provider holds it, so you can switch any time
(Cloud Storage page → **Use this**) and old photos keep working.

1. **Local** - files in `backend/uploads`, served at `/files/...`. Start here.
2. **Cloudinary** (easiest cloud) - sign up → Dashboard → copy 3 keys into `.env`. Thumbnails are generated by Cloudinary from the URL.
3. **AWS S3 / Cloudflare R2** (the real-world one):
   - Make a **private** bucket, an IAM user limited to it, add bucket **CORS** (`PUT`, `GET`, origins `http://localhost:5173` and `null`).
   - Uploads then go **browser → bucket directly** using a *presigned URL* (`POST /storage/presign`), and the API only registers the file
     (`POST /photos/register`) - your server never carries the bytes. Copy-paste IAM/CORS JSON is on the Cloud Storage page.
   - Add **CloudFront** (S3) or a public R2 domain and set `S3_PUBLIC_BASE_URL` for fast cached delivery.

**Cost traps:** data-transfer-out and per-request charges (S3), transformation credits (Cloudinary). Never make a bucket public, never commit keys.

### Roadmap - what to add next (each is a nice weekend project)
- **Auto-tagging / faces:** AWS Rekognition `detect_labels` or Google Vision → write results into `photo.tags` (search already reads tags).
- **Thumbnails on upload:** S3 event → AWS Lambda (Pillow) → writes `thumbs/…`, then drop server-side thumbnailing for the S3 path.
- **Bin in the cloud:** S3 lifecycle rule on a `bin/` prefix instead of the APScheduler purge job.
- **Background jobs:** SQS + a worker, or Celery + Redis, for ZIP exports and bulk processing.
- **Logs & alarms:** CloudWatch (EC2/Lambda) for the structured logs the API already emits.
- **Better search:** MongoDB Atlas Search (typo-tolerant, ranking).
- **Alternatives:** Firebase Storage or Supabase Storage = one more `StorageProvider` subclass (4 methods).
- **Deploy:** Docker the backend → Render / Railway (easy) or AWS EC2 / ECS (learning). Then point `VITE_API_URL` at it.

## 5. API tour (Swagger → `/docs`)

`/auth/*` · `/photos` (list, ids, upload, register, bulk, download-zip, `{id}`, `{id}/download`) · `/albums` · `/share` (+ public page `/s/{token}`) ·
`/bin` · `/storage/summary|provider|presign` · `/analytics/*` · `/notifications`

Bulk example: `POST /photos/bulk {"ids":[...], "action":"delete"}` - actions: `favorite, unfavorite, delete, restore, delete_forever, move, remove_from_album`.

## 7. Security notes
- `.env` is git-ignored. Rotate your Atlas password if a zip containing it was ever shared.
- Images are validated by their **bytes** (Pillow), filenames sanitised, storage keys are UUIDs, quota enforced, auth routes rate-limited.
- Local image files are served by unguessable UUID paths without a login (browsers can't send a token with `<img>`); use S3 presigned URLs if you need stricter privacy.

## 8. Design decisions worth knowing
- **PyJWT + built-in scrypt** instead of python-jose/passlib (both break on recent Python versions).
- A photo belongs to at most **one album** (simple model, matches your original `album` field).
- Editing never overwrites: **Save as copy**.
- Dates are grouped by EXIF "taken" time, falling back to upload time.
